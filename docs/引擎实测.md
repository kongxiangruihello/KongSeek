# 搜索引擎实测（2026-10-27）

数据来自 `swift run -c release ksbench new|legacy`（当时位于 KongFetch 仓库 core-index 分支的同一引擎）。"3.2" 指 KongFetch 3.2 的代码。

环境：Apple 芯片 Mac，macOS 27.0.1，Swift 6.4，release 编译。合成目录树共 300,450 个文件、25,299 个文件夹；对比时两边使用相同的排除规则（3.2 规则），收录条目同为 220,358 个。

| 项目 | 3.2 | 新引擎 |
| --- | --- | --- |
| 建立索引 | 5,678 ms | 1,020 ms（读目录 523 + 计算检索键 497） |
| 索引常驻内存 | 431 MB | 84 MB |
| 索引文件大小 | 36.2 MB（JSON） | 20.0 MB（二进制） |
| 保存 / 载入索引 | 631 / 1,045 ms | 12 / 27 ms |
| 单次查询（模糊名称，12 条查询） | 5.9–7.6 秒 | 0.6–2.8 ms |
| 单次查询（名称及路径，12 条查询） | 2.4–9.8 秒 | 0.8–4.9 ms |
| 带 `ext:`、短语、排除词的查询 | — | 0.4–3.7 ms |
| 逐字输入 "contract"（7 次查询） | 53.9 秒 | 3.9 ms（收窄）/ 8.0 ms（不收窄） |

- 两边 24 组查询的命中数完全相同；`MatchingParityTests`、`QueryParityTests`、`PinyinFastPathTests` 另对每个文件的分数和筛选结果逐一比对，结果一致。
- 3.2 一栏只计打分循环（单线程），不含 3.2 应用为每个结果读取文件属性的开销，因此对 3.2 偏有利；它的 NSCache 上限为 5 万条，少于条目数，缓存会被反复冲掉。
- 拼音按"连续汉字段"整段转写并缓存（系统转写会按词组读音，如"重庆"读 chong qing），段间按系统规则补空格。基准对全部 165,886 个含中文的文件名逐一与整串转写核对，0 处不一致。合成树的汉字段重复率高，缓存命中多；真实文件名更分散，计算检索键会慢一些，最坏情况等于逐个整串转写（本树上约 7 秒）。
- 使用新的默认排除规则时收录 315,494 个条目，多出的 95,136 个位于名为 `build`、`Library` 的用户文件夹中（3.2 会跳过）。这个差额取决于合成树的构造，只说明规则差异。
